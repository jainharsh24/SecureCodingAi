Abstract
 
Software security vulnerabilities remain a prevalent and costly threat to global digital 
infrastructure. While traditional competitive programming and educational coding platforms 
(such as LeetCode, HackerRank, and Codewars) effectively cultivate algorithmic proficiency, 
they focus exclusively on functional correctness while ignoring software security 
vulnerabilities. Conversely, offensive cybersecurity platforms (such as PortSwigger Web 
Security Academy, TryHackMe, and Hack  The Box) emphasize penetration testing and 
exploitation rather than the constructive software engineering disciplines required to write 
secure source code. Furthermore, modern generative AI coding assistants frequently produce 
functionally acceptable yet insecure code, exacerbating the vulnerability epidemic. 
This report presents SecureCode AI, an interactive, web -based secure coding practice and 
automated assessment platform engineered to cultivate defensive programming competencies 
from the ground up. SecureCode AI implements a novel dual -stage evaluation architecture: 
Stage 1 executes dynamic functional unit testing within an isolated sandbox (via Judge0), while 
Stage 2 performs multi -engine static and AI -assisted security analysis combining abstract 
syntax tree (AST) rules (Semgrep), bytecode dataflow inspection (SpotBugs/FindSecBugs), 
and contextual large language model advisory (Groq LLaMA -3). To prevent trial -and-error 
guessing and superficial code modification, SecureCode AI introduces an active catalog of 45 
staged injection challenges (spanning SQL, NoSQL, OS Command, LDAP, XPath, 
Header/CRLF, and Code Injection), a rate -limiting five -attempt window, interactive 
conceptual understanding quizzes, and a multi -factor learning scoring engine that holistically 
weights Functional Correctness (25%), Security Correctness (45%), Conceptual 
Understanding (15%), and Independent Problem Solving (15%). 
The system was engineered using Spring Boot 3, Java 25, PostgreSQL, Flyway migrations, 
and a responsive web application client. Empirical validation across 80 automated unit, 
integration, and security test suites demonstrates zero false passes on vulnerable code, flawless 
consensus arbitration across disparate static analysis outputs, and sub -500ms median 
evaluation latency for local static engines. SecureCode  AI bridges the critical pedagogical 
chasm between algorithmic programming and software security, empowering developers to 
construct verifiably secure systems before deployment. 
Keywords: Secure Code Generation, Automated Programming Assessment Systems (APAS), Static 
Application Security Testing (SAST), Injection Attacks, Dual -Stage Evaluation, Learning Analytics, 
Large Language Models (LLM), Software Engineering Education.

Chapter 1 
Introduction
 
Modern society depends unconditionally on complex software systems spanning banking, 
healthcare, e -commerce, national defense, and industrial automation. However, software 
security vulnerabilities continue to proliferate at an alarming rate, inflicting trillions of dollars 
in global economic damages and compromising billions of user records annually. Historically, 
cybersecurity initiatives have focused primarily on perimeter defenses, post -deployment 
intrusion detection, and reactive patch management. While perimeter security is indispensable, 
modern software engineering paradigms increasingly emphasize “Shift -Left” 
methodologies—integrating security directly into the earliest phases of the software 
development lifecycle (SDLC). The fundamental premise of th e Shift-Left movement is that 
writing secure code from the very beginning is exponentially cheaper, more resilient, and more 
effective than remediating flaws in production systems. 
Despite widespread industry consensus regarding the necessity of secure coding, contemporary 
software developers entering the engineering workforce remain ill -equipped to write robust, 
defensible code. Traditional computer science education and commercial training platforms 
concentrate almost exclusively on algorithmic correctness, performance optimization, and 
rapid functional prototyping, relegating security to an afterthought. SecureCode  AI is 
conceived and engineered to resolve this fundamental educational deficit by providing a 
comprehensive, interactive, web -based platform that unifies hands -on vulnerability fixing, 
automated dual -stage evaluation, explainable security feedback, and lo ngitudinal learning 
analytics. 
1.1 Motivation
 
The motivation behind SecureCode  AI arises from a critical, systemic disconnect between 
software development pedagogy and the threat reality of contemporary digital systems. Over 
the past decade, automated programming assessment systems (APAS) such as LeetCode, 
HackerRank, CodeChef, and Codewars have revolutionized how developers practice 
programming. Millions of students and practicing software engineers routinely spend hundreds 
of hours solving algorithmic challenges to prepare for technical interviews and optimize code 
performance. However, every single one of these mainstream platforms evaluates submissions 
based on an archaic criterion: functional input -output correctness. If a candidate’s solution 
computes the expected mathematical output within the allotted memory and CPU time, the 
platform awards full credit —even if the underlying implementation contains catastrophic

vulnerabilities such as unparameterized database concatenation (SQL Injection), arbitrary 
operating system command execution (Command Injection), or insecure deserialization. This 
functional-only paradigm inadvertently trains an entire generation of develo pers to consider 
security irrelevant, reinforcing sloppy coding habits that carry directly into enterprise 
codebases. 
This pedagogical crisis is drastically amplified by the explosive adoption of generative 
artificial intelligence (GenAI) coding assistants, such as GitHub Copilot, OpenAI ChatGPT, 
and Claude. Recent empirical software engineering studies [1], [2], [4] demonstrate that while 
LLMs accelerate code production, between 35% and 45% of LLM -generated code snippets 
contain exploitable Common Weakness Enumerations (CWEs). Developers who lack 
foundational secure coding training routinely accept and integrate these vul nerable AI 
suggestions without scrutiny. Furthermore, when developers attempt to ask AI assistants to 
remediate security warnings, the models frequently introduce subtle secondary vulnerabilities 
or hallucinate non -existent security APIs [4], [5]. Conseque ntly, there is an urgent and 
unprecedented motivation to establish dedicated pedagogical infrastructure that actively 
teaches developers how to identify vulnerabilities, refactor insecure constructs into defensible 
architectures, and rigorously verify both functional and security properties. 
1.1.1 Need of the Problem
 
The necessity of addressing secure coding at the educational level is underscored by several 
critical industry and empirical software engineering factors: 
• 
 Academic Curriculum Deficit: Industry surveys and academic mapping studies (e.g., Gasiba 
et al. [25], Torbunova et al. [20]) confirm that over 75% of computer science graduates 
receive no formal training in secure coding practices throughout their undergraduate 
education. Security is typically taught as an elective theoretical course focused on 
cryptography or network protocols, with zero hands-on secure programming exercises.
 
• 
 Offensive vs. Defensive Asymmetry: Leading offensive training environments—such as 
PortSwigger Web Security Academy, TryHackMe, and Hack The Box—do an admirable job 
of teaching penetration testing and vulnerability exploitation. However, knowing how to 
exploit an application using SQLMap or Burp Suite does not translate into the software 
architectural skills required to write secure code. Developers need constructive practice 
writing defensible logic, not merely executing exploits.
 
• 
 Unfriendly Tooling and Inactionable Feedback: Standard static application security testing 
(SAST) tools used in enterprise pipelines (such as SonarQube, Semgrep, and SpotBugs) are 
engineered for professional security engineers rather than novices. Their output consists of 
dense, acronym-heavy reports with high false-positive rates that bewilder junior developers

without explaining the fundamental architectural flaw or providing contextual remediation

• 
 Single-Scanner Vulnerability Blind Spots: Empirical evaluations by Dai et al. [1] and Bi et al.

30% of critical vulnerabilities due to syntax limitations and taint-tracking blind spots. An 
effective educational assessment platform must synthesize multiple complementary analysis 
techniques—combining AST matching, bytecode dataflow, and contextual AI reasoning—to 
ensure high-fidelity evaluation.
 
• 
 Superficial Remediation and Lack of Conceptual Verification: When learners use modern AI 
assistants to complete coding exercises, they frequently engage in passive copy-pasting 
without understanding the underlying security principles. Without an integrated mechanism 
to assess conceptual understanding and reward independent problem-solving, students cannot 
achieve true security competence.

Chapter 2 
Problem Statement & Requirements Engineering
 
This chapter formalizes the engineering problem addressed by SecureCode AI, details the 
architectural features of the proposed platform, enumerates the precise technical objectives, 
and specifies the functional and non -functional requirements that govern t he system's design 
and empirical evaluation. 
2.1 Problem Statement
 
Modern software development platforms and automated programming assessment systems 
suffer from a severe architectural and pedagogical limitation: they evaluate student code 
submissions purely on functional correctness (input -output matching), completely ig noring 
code security, architectural hygiene, and vulnerability resistance. Consequently, novice 
developers routinely write, test, and submit code containing severe security vulnerabilities —
such as SQL Injection, Command Injection, and Path Traversal—and receive full credit as long 
as the functional test cases pass. This establishes negative reinforcement, teaching developers 
that insecure coding practices are acceptable as long as functional requirements are met. 
Furthermore, existing cybersecurity learning environments are heavily skewed toward 
offensive security (penetration testing, exploit scripting, and red teaming) rather than defensive 
software engineering. Platforms such as PortSwigger Web Security Academy or Hack The  
Box train users to break into vulnerable systems using automated attack tools, but provide no 
integrated code editor, no compiler feedback, and no automated mechanism to evaluate 
whether a user can write secure, production -ready source code that satisfies  business logic 
while resisting malicious payloads. Meanwhile, commercial enterprise secure coding tools are 
closed, prohibitively expensive, and rely on multiple -choice quizzes or micro -lessons rather 
than authentic, hands-on code refactoring. 
The problem addressed in this project is to develop and empirically validate a unified, 
automated secure programming practice and assessment platform —SecureCode AI—that 
evaluates both functional correctness and security properties, integrates multi -engine static 
security analysis (Semgrep, SpotBugs, and Groq  LLM), prevents superficial trial -and-error 
guessing through attempt -limiting windows and prerequisite learning graphs, verifies 
conceptual comprehension via interactive assessments, and calculates an auditable, four-pillar 
learning score.

2.2 Features of the System
 
• 
 Interactive Browser-Based Code Editor: An in-browser code editor featuring Monaco Editor / 
React, syntax highlighting, keyboard shortcuts, starter code loading, and responsive split-
pane layout showing problem descriptions, constraints, and test suites side-by-side.
 
• 
 Active Injection Challenge Catalog: A curated curriculum of 45 staged injection challenges 
structured across 6 critical injection subtypes (SQL, NoSQL, OS Command, LDAP, XPath, 
Header/CRLF, Code Injection) and 4 difficulty tiers (Basic, Easy, Medium, Hard).
 
• 
 Dual-Stage Evaluation Engine: A staged execution architecture where dynamic functional 
unit testing (Judge0 sandbox) is evaluated first. Only solutions that successfully compile and 
pass all functional test cases advance to the static security evaluation stage, preventing 
wasted computational overhead on broken submissions.
 
• 
 Multi-Engine Security Analysis Pipeline: Simultaneous scanning of student source code 
using Semgrep (AST pattern matching and taint tracking), SpotBugs with FindSecBugs 
(bytecode dataflow analysis), and Groq LLaMA-3 (contextual reasoning and architectural 
advice).
 
• 
 Evidence Normalization and Consensus: An automated arbitration module that parses 
disparate findings from all scanners, resolves discrepancies, filters false positives, and assigns 
a normalized security verdict (VERIFIED_SAFE, TARGETED_VULNERABILITY, 
UNVERIFIED) with an associated evidence confidence score.
 
• 
 Five-Attempt Rate-Limiting Window: A rate-limiting mechanism that allocates exactly 5 
graded submission attempts per challenge across a rolling 7-day window. This curtails rapid 
trial-and-error guessing and compels learners to think deliberately before submitting.
 
• 
 Tiered Hint Assistance Engine: A three-level assistance engine providing Conceptual Hints (-
5 pts), Implementation Hints (-10 pts), and Solution Reveals (-15 pts) to balance guided 
learning with independent achievement.
 
• 
 Conceptual Understanding Assessments: Post-submission comprehension verification 
requiring learners to answer conceptual multiple-choice questions and submit written 
architectural justifications explaining how their fix prevents vulnerability exploitation.
 
• 
 Four-Pillar Overall Learning Score: A mathematical scoring model combining Functional 
Correctness (25%), Security Correctness (45%), Conceptual Understanding (15%), and 
Independent Problem Solving (15%) into a verified 100-point score, enforcing a 70-point 
Solved threshold and 90-point Mastery threshold.
 
• 
 Prerequisite Progression Graph: A directed acyclic graph (DAG) enforcing prerequisite 
foundational challenges before advanced challenges can be unlocked, ensuring structured 
pedagogical progression.

• 
 Learning Analytics and Performance Tracking: Comprehensive visual dashboards displaying 
difficulty-wise completion rates, functional pass accuracy, longitudinal learning trends, and 
vulnerability remediation history.
 
• 
 Learning Hub Educational Repository: A dedicated educational resource section detailing 
injection definitions, real-world attack vectors, impact scenarios, and defensive programming 
principles for each vulnerability category.
 
2.3 Objectives
 
The technical and pedagogical development of SecureCode AI is guided by the following 
concrete objectives: 
• 
 1. Full-Stack Architectural Engineering: Design and construct a scalable, microservices-
ready client-server architecture utilizing Spring Boot 3, Java 25, PostgreSQL, and a modern 
responsive web client.
 
• 
 2. Sandboxed Functional Execution: Implement a sandboxed execution environment 
integrating Judge0 API to compile and dynamically test Java source code against hidden and 
visible test cases within 2.0s execution boundaries.
 
• 
 3. Multi-Engine Security Consensus: Integrate, orchestrate, and normalize findings from 
Semgrep, SpotBugs, and Groq LLM into an auditable security consensus engine with zero 
false passes on vulnerable test cases.
 
• 
 4. Challenge Curriculum Development: Populate and maintain an active catalog of 45 staged 
challenges across 6 injection subtypes with complete reference implementations and verified 
automated test suites.
 
• 
 5. Pedagogical Scaffolding & Rate Limiting: Deploy attempt-limiting windows (5 attempts /

Chapter 3 
Literature Review
 
The development of SecureCode AI is situated at the intersection of four prominent software 
engineering and computer science education disciplines: (1) AI -assisted secure code 
generation and large language model (LLM) evaluation, (2) Automated Programming 
Assessment Systems (APAS) and  pedagogical feedback mechanisms, (3) static application 
security testing (SAST) and vulnerability detection benchmarking, and (4) empirical studies 
on secure programming pedagogy and industry training deficits. This chapter presents a 
systematic review of 27 peer-reviewed research works, critically analyzes existing systems and 
their limitations, formalizes the research gap, and articulates the architectural contributions of 
SecureCode AI. 
3.1 Existing Systems
 
The surveyed literature reveals intense global research activity focused on software 
vulnerability remediation, automated assessment, and generative AI code generation. We 
categorize the existing literature into four thematic clusters: 
3.1.1 AI-Assisted Secure Code Generation and LLM Pitfalls
 
In recent years, the deployment of large language models for source code generation has 
transformed developer workflows. However, rigorous empirical evaluations demonstrate 
persistent, critical security vulnerabilities in AI -generated code. Dai et al. [1] (ICSE '26) 
rethought the evaluation paradigms of secure code generation across 2,341 benchmark tasks, 
discovering that existing evaluation schemes evaluate security and functional correctness 
independently. Crucially, Dai et al. demonstrated that conventio nal evaluation pipelines 
relying on a single static scanner miss over 20% of critical vulnerabilities, proving the absolute 
necessity of joint functional-security evaluation and multi-scanner verification. Patir et al. [2] 
conducted a comprehensive Systema tization of Knowledge ( SoK) across hundreds of secure 
code generation interventions (prompting, fine -tuning, decoding constraints, and agentic 
feedback). Their KAUGE measurement framework established that a developer or model 
'knowing' a security principle does not translate into ' actuating' that principle correctly in 
complex codebases. Zhou et al. [3] surveyed 58 papers on LLMs for vulnerability detection 
and repair, concluding that while LLMs excel at contextual reasoning, they require grounding 
with deterministic static analysis  tools to suppress hallucinations. Yan et al. [4] investigated 
LLM self-repair on SecurityEval (69 CWEs) and SecCodePLT, finding that simple 'fix this 

=== PAGE 23 ===
22 | P a g e 
vulnerability' prompts fail 60% of the time; effective repair requires precise, contextualized 
hints referencing specific AST constructs. Belozerov, Barclay, and Sami [5], [27] analyzed 
2,315 GPT-generated programs from the DevGPT dataset, proving that automated static code 
analysis coupled with LLM advisory feedback creates a highly effective remediation pipeline. 
Alwageed and Khan [8], [17], [18] constructed a comprehensive taxonomy of 109 concrete 
GenAI-driven secure coding practices across 10 vulnerability categories, emphasizing input 
validation and query parameterization. Nocera et al. [24] deployed ChatGPT in an 
undergraduate web engineering course of 105 students, showing that while conversational AI 
aids student comprehension of attack surfaces, students frequently introduce syntax and 
runtime errors during manual remediation without sandboxed functional execution. 
3.1.2 Automated Programming Assessment Systems (APAS) and Feedback
 
Automated Programming Assessment Systems (APAS) have been extensively studied as 
mechanisms to scale computing education. Combéfis  [9] reviewed and classified automated 
code assessment tools, observing that almost all current platforms focus purely on functional 
black-box testing (input/output matching) or static code formatting (linters), completely 
omitting security and defensibili ty evaluations. Rahman, Watanobe, Shirafuji, and Hamada 
[10] surveyed automated code evaluation systems and analysis resources, highlighting that 
modern APAS require multi-stage grading pipelines that evaluate runtime behavior, structural 
quality, and vulnerability resistance. Frankford et al. [11] surveyed feedback modalities across 
automated assessment platforms, concluding that binary pass/fail grades induce frustration; 
novice learners require multi-tiered, formative feedback combining compiler diagnostics, hint 
ladders, and actionable remediation advice. Frankford et al. [12] subsequently developed an 
online browser -based IDE for automated assessment, demonstrating that zero -install web 
environments significantly reduce onboarding friction and increase student submission 
velocity. Sauerwein et al. [14] ( ITiCSE 2023) established a formal Success Model for APAS 
used as formative assessment tools, proving that system trust, immediate feedback loops, and 
progressive difficulty scaffolding directly determine student learning gains and self -efficacy. 
Nam et al.  [15] explored using LLMs to aid student code comprehension, illustrating that 
contextual AI explanations accelerate novice understanding of abstract programming concepts 
when constrained by explicit rubrics. 
3.1.3 Vulnerability Detection Benchmarking and SAST Quality
 
The efficacy of automated security assessment depends fundamentally on the accuracy and 
robustness of underlying vulnerability detection engines. Guo and Bettaieb [6] investigated 
quality issues across 54 vulnerability detection datasets, discovering sever e label noise,

sampling biases, and high class  imbalances that compromise machine -learning-based 
vulnerability classifiers. Bi et al. [7] surveyed benchmarking approaches for vulnerability 
detection, providing a rigorous framework for evaluating static analyzers. Their findings 
demonstrate that static application security testing (SAST) tools exhibit substantial variance: 
AST-based pattern matchers (such as Semgrep) excel at syntax and call-site matching but miss 
cross-function dataflows, whereas bytecode analyzers (such as SpotBugs and FindSecBugs ) 
track taint propagation effectively but produce verbose false alarms on complex frameworks. 
Shahriar et al. [16] demonstrated that IDE-based security plugin interventions provide valuable 
point-of-coding reminders but fail to motivate students without ga mification and automated 
grading. Naeem et al. [26] reviewed cyber security enhancements and vulnerability 
identification benchmarks, confirming that hybrid detection pipelines combining rule -based 
heuristics with deep learning or LLMs yield superior coverage. 
3.1.4 Secure Programming Pedagogy and Industry Competency Gap
 
Empirical studies consistently demonstrate an acute secure coding competency gap across 
academia and the software industry. Gasiba , Lechner, Pinto -Albuquerque, and Mendez [25] 
conducted a landmark large -scale industrial survey of 194 professional software developers 
across Siemens and major tech enterprises. Their empirical findings revealed that over 80% of 
industrial software engin eers possess limited awareness of fundamental secure coding 
guidelines (OWASP Top 10, SANS Top 25) and lack hands -on experience refactoring 
vulnerable code. In response, Gasiba  et al. [22], [23] pioneered the design of secure coding 
challenges and serious cybersecurity games (e.g., CyberSecurity Challenge and Sifu), proving 
that interactive, puzzle -based code -repair exercises dramatically improve secure coding 
retention compared to passive compliance lectures. Bappy et al. [13] (SOUPS 2026) conducted 
a behavioral study showing that AI coding assi stants transform developer security awareness 
from preventive to reactive: developers rely heavily on AI to fix bugs, often deactivating their 
own critical scrutiny. Amburi et al. [19] (ICPEC 2025) explored GenAI for developer training, 
proving that LLMs can serve as interactive pedagogical tutors if properly constrained by secure 
coding rubrics. Torbunova , Ashraf, and Porres [20] mapped security teaching across 
computing courses, revealing that fewer than 5% of introductory programming curricula 
incorporate security. Malinka et al. [21] introduced real -world bug bounty programs into 
university secure coding courses, proving that hands-on vulnerability interaction significantly 
enhances defensive mindset development.

3.2 Limitations of Existing Systems
 
Despite significant advancements across individual research areas, existing systems and 
commercial tools exhibit several profound architectural, pedagogical, and technical limitations 
when applied to secure coding education: 
• 
 1. Functional-Only Evaluation Antipattern: Mainstream competitive programming platforms 
(LeetCode, HackerRank, Codewars) evaluate solutions strictly against functional test cases. 
A solution that concatenates raw SQL queries or invokes Runtime.getRuntime().exec() 
receives full points as long as the expected output matches, reinforcing dangerous coding 
antipatterns.
 
• 
 2. Offensive vs. Defensive Asymmetry: Leading cybersecurity platforms (PortSwigger Web 
Security Academy, TryHackMe, Hack The Box, OWASP Juice Shop) focus almost 
exclusively on offensive exploitation—teaching students how to use automated scanners, 
intercept HTTP proxies, and inject SQL payloads. They do not teach how to write defensible, 
production-quality source code or provide automated code-level grading.
 
• 
 3. Proprietary and Non-Authentic Coding Modalities: Enterprise training platforms (Secure 
Code Warrior, Kontra, RangeForce) are closed, proprietary, and cost-prohibitive for 
academic institutions. Furthermore, their learning models frequently rely on multiple-choice 
quizzes, code inspection puzzles, or video modules rather than authentic, end-to-end coding 
in an interactive compiler environment.
 
• 
 4. Single-Scanner Blind Spots and Fragile Heuristics: As demonstrated by Dai et al. [1] and 
Bi et al. [7], single static analysis tools suffer from high false-negative rates (>20%), missing 
critical vulnerabilities due to syntax variances and dynamic taint paths. Existing educational 
tools do not combine multiple complementary SAST engines with AI arbitration.
 
• 
 5. Lack of Conceptual Comprehension Verification: When existing platforms incorporate 
conversational AI, the models frequently hallucinate non-existent security libraries or suggest 
superficial fixes that break functionality. Crucially, existing platforms provide no mechanism 
to verify whether a student genuinely understands the vulnerability or merely pasted an AI-
generated snippet.
 
• 
 6. Uncontrolled Trial-and-Error Guessing: Standard coding platforms permit unlimited rapid-
fire submissions. Students routinely engage in brute-force trial-and-error debugging—
tweaking arbitrary lines until a test passes—bypassing the reflective, analytical thinking 
essential for secure software engineering.

SecureCode AI is engineered specifically to eliminate these limitations through a unified, full-
stack architectural framework that bridges competitive coding, automated multi -engine

 Dual-Stage Execution Gate: A decoupled evaluation engine where Stage 1 executes dynamic

Chapter 4 
Design and Implementation
 
This chapter presents the architectural design, formal modeling, algorithmic formulations, 
relational data structures, and implementation mechanics of SecureCode  AI. The platform is 
engineered as a robust, decoupled, multi -tier system built on Spring Boot 3, Java 25, 
PostgreSQL, and a responsive web application client, integrating sandboxed dynamic 
execution with a multi-engine static security analysis and AI advisory pipeline. 
4.1 System Architecture
 
SecureCode AI follows a modern, highly modular, client -server architecture organized into 
four primary functional tiers, as illustrated in Fig 4.1.1: 
• 
 1. Presentation Tier (Client Web Application): The client application provides an intuitive, 
responsive user interface accessible via modern web browsers on desktop, laptop, and tablet 
devices. Engineered with HTML5, CSS3, Bootstrap, and vanilla/React JavaScript 
components, it features an embedded Monaco code editor, real-time submission consoles, 
dynamic learning analytics dashboards, interactive hint dialogs, and administrative 
management panels.
 
• 
 2. Application & Logic Tier (Spring Boot Backend): The backend server is implemented in 
Spring Boot 3 (Java 25) following a domain-driven, layered service architecture. It 
encapsulates six core business service modules: UserService (authentication, profile, and 
JWT token management), ChallengeService (catalog retrieval, difficulty filtering, and 
prerequisite DAG evaluation), SubmissionService (submission intake, attempt window 
enforcement, and persistence), FeedbackService (remediation rendering, fix advice, and 
CWE linking), ProgressService (learning score computation and analytics aggregation), and 
AdminService (challenge CRUD and user management).
 
• 
 3. Dual-Stage Evaluation Engine Tier: The core computational backbone of SecureCode AI. 
To optimize throughput and guarantee security isolation, the evaluation engine is split into 
two specialized sub-stages: (a) Functional Evaluation Runner (integrating the Judge0 API 
sandbox for isolated compilation and dynamic execution against unit test suites), and (b) 
Security & AI Evaluation Pipeline (orchestrating Semgrep AST analysis, 
SpotBugs/FindSecBugs bytecode analysis, and Groq LLaMA-3 contextual LLM advisory).
 
• 
 4. Persistence & Data Tier (PostgreSQL): Enterprise-grade relational persistence powered by 
PostgreSQL, managed through version-controlled Flyway schema migrations (V1 to V21). 
The database stores users, challenge definitions, test suites, immutable submission records,

raw evaluator outputs, normalized security findings, hint view logs, and conceptual 
understanding assessments.

4.2 Working of the System
 
The end -to-end operational workflow of SecureCode AI is designed to guide learners 
seamlessly through a structured defensive programming cycle while enforcing rigorous 
academic and security checks: 
• 
 Step 1 (Authentication & Session Initialization): A student registers or authenticates using 
credentials. The authentication service validates credentials using PBKDF2 hashing and 
issues a Bearer JWT token valid for the active session.
 
• 
 Step 2 (Challenge Selection & Prerequisite Verification): The student browses the Challenge 
Catalog. The PrerequisiteAccessService evaluates the student's completed submission graph 
against prerequisite edges. Locked challenges display clear prerequisite requirements, while 
unlocked challenges display difficulty badges, CWE tags, and remaining attempt counters.
 
• 
 Step 3 (Vulnerability Exploration & Code Refactoring): Upon selecting a challenge, the 
workspace loads the problem description, vulnerable starter code, functional constraints,

visible test cases, and real-world vulnerability impact context. The student reviews the 
insecure code in the Monaco Editor and formulates a defensive refactoring strategy.
 
• 
 Step 4 (Tiered Hint Assistance): If the student encounters conceptual roadblocks, they may 
open the Tiered Hint modal. Viewing a Conceptual Hint deducts 5 points from the 
independence score; an Implementation Hint deducts 10 points; a Full Solution Reveal 
deducts 15 points. All views are logged immutably in hint_view_events.
 
•

• 
 Step 6 (Stage 1 - Sandboxed Functional Evaluation): The SubmissionService transmits the 
source code to the Judge0 sandbox. Judge0 compiles and executes the code against hidden 
and visible test cases. If any test case fails, compilation errors occur, or runtime limits (2.0s 
CPU / 128MB) are exceeded, evaluation halts immediately, returning detailed execution diffs 
to the student.
 
• 
 Step 7 (Stage 2 - Multi-Engine Security Analysis): If functional execution achieves a 100% 
PASS verdict, the system automatically triggers Stage 2. The source code is scanned in 
parallel by Semgrep (AST pattern matching), SpotBugs/FindSecBugs (bytecode dataflow 
analysis), and Groq LLaMA-3 (contextual semantic advisory).
 
• 
 Step 8 (Evidence Normalization & Consensus Arbitration): The 
SecurityFindingEvidenceCodec and SecurityCorrectnessScoringService normalize disparate 
outputs into a unified verdict: VERIFIED_SAFE (no vulnerabilities detected), 
TARGETED_VULNERABILITY (the challenge's targeted flaw remains unmitigated), or 
UNVERIFIED (evaluator divergence).
 
• 
 Step 9 (Conceptual Understanding Assessment): Upon achieving a functionally correct and 
safe submission, the student is prompted to complete a post-submission Conceptual 
Understanding Quiz. The student answers multiple-choice questions regarding attack vectors 
and inputs a written architectural justification explaining why their defensive implementation 
breaks the exploit path.
 
• 
 Step 10 (Multi-Pillar Scoring & Dashboard Analytics): The OverallLearningScoreService 
computes the final 100-point learning score combining Functional Correctness (25), Security 
Correctness (45), Understanding (15), and Independence (15). Results are displayed on the 
Submission Analysis page, and progress metrics update across the student dashboard.

4.6 Multi-Engine Security Architecture & Consensus
 
A foundational contribution of SecureCode AI is its multi -evaluator consensus mechanism, 
engineered to eliminate the 20%+ false -negative rate inherent in single -scanner SAST 
platforms [1], [7]. SecureCode AI deploys three complementary security evaluators: 
• 
 1. Semgrep SAST Engine: Operates directly on the Java Abstract Syntax Tree (AST). 
Semgrep utilizes curated YAML rule definitions located in tools/semgrep/rules/ targeted to 
specific injection patterns (e.g., detecting java.sql.Statement.executeQuery with string 
concatenation, Runtime.getRuntime().exec with unsanitized arguments, or LDAP search 
filters with raw input). Semgrep delivers deterministic, millisecond-fast pattern recognition.
 
• 
 2. SpotBugs / FindSecBugs Engine: Performs interprocedural bytecode dataflow and taint-
tracking analysis on compiled .class artifacts. Utilizing the FindSecBugs security plugin, 


=== PAGE 38 ===
37 | P a g e 
SpotBugs inspects data propagation from untrusted input sources to sensitive sinks, 
identifying taint vulnerabilities that span multiple methods or classes.
 
• 
 3. Groq LLM Contextual Advisor: Powered by Groq's high-speed inference engine running 
LLaMA-3. Unlike static linters that search for static syntactic signatures, the LLM analyzes 
the overall architectural intent of the code, identifying subtle logic flaws, improper allow-list 
implementations, and insufficient sanitization routines while generating natural-language 
remediation guidance.
 
To reconcile conflicting outputs, the NormalizedEvaluatorEvidence and 
SecurityEvidenceSummary services implement a strict fail -closed consensus rule: if ANY 
valid static scanner detects an active targeted vulnerability matching the challenge's CWE 
subtype, the security verdict is immediately classified as TARGETED_VULNERABILITY, 
and Security Corre ctness receives 0 points. A VERIFIED_SAFE verdict requires 100% of 
available evaluators to affirm that no targeted vulnerabilities exist. This zero -insecure-pass 
guarantee ensures that students can never bypass security requirements through scanner 
discrepancies. 
4.7 Algorithms and Mathematical Formulations
 
4.7.1 Dual-Stage Evaluation Gate Algorithm
 
Let C be the target challenge, S the submitted source code, and T = {t1, t2, ..., tn} the set of 
functional unit tests. Stage 1 dynamic evaluation produces a functional verdict V_func in 
{PASS, FAIL, COMPILE_ERROR, TIMEOUT}. Stage 2 security analysis is invoked if and 
only if V_func = PASS: 
 
Gate(S, T) =  
  Reject(V_func),                           if V_func != PASS 
  TriggerSecurityPipeline(S, C),            if V_func == PASS 
4.7.2 Static Analysis Evidence Normalization Algorithm
 
Let E = {e1, e2, ..., em} be the set of completed security evaluators (Semgrep, SpotBugs, 
LLM). For each evaluator e_i, let v_i in {SAFE, VULNERABLE, UNAVAILABLE} be its 
verdict, and let F_i be the set of detected findings. The targeted vulnerability set is computed 
as: 
 
F_targeted = Union_{i=1}^m { f in F_i | CWE(f) == CWE(C) and v_i == VULNERABLE } 
 
The normalized security verdict V_sec is derived as: 

=== PAGE 39 ===
38 | P a g e 
  TARGETED_VULNERABILITY,   if |F_targeted| > 0 
  VERIFIED_SAFE,            if |F_targeted| == 0 and forall i (v_i == SAFE) 
  UNVERIFIED,               if valid evaluators == 0 or conflicting evidence 
4.7.3 Four-Pillar Overall Learning Score Formulation
 
The Overall Learning Score S_overall in [0, 100] is calculated across four bounded 
components: 
 
S_overall = S_func + S_sec + S_und + S_ind 
 
where: 
  S_func in [0, 25]: Functional correctness score awarded upon passing unit tests (Judge0). 
  S_sec in [0, 45]: Security correctness score. S_sec = 45 if V_sec = VERIFIED_SAFE; 
S_sec = 0 if V_sec = TARGETED_VULNERABILITY. 
  S_und in [0, 15]: Conceptual understanding score assessed via post-submission multiple-
choice and written justifications. 
  S_ind in [0, 15]: Independent problem-solving score based on hint usage: 
      S_ind = 15 (No hints viewed) 
      S_ind = 10 (Conceptual hint viewed) 
      S_ind = 5  (Implementation hint viewed) 
      S_ind = 0  (Solution reveal viewed) 
 
Thresholds: A challenge is marked SOLVED when S_func + S_sec >= 70. A challenge 
achieves MASTERY when S_overall >= 90 and min(S_func, S_sec, S_und, S_ind) > 10. 
4.7.4 Attempt Windowing & Prerequisite Progression
 
Submission rate-limiting restricts attempts to exactly 5 per rolling 7-day window W per user 
u and challenge C: 
 
WindowCheck(u, C, now) =  
  ResetWindow(u, C, attempts=1),          if now - window_start > 7 days 
  IncrementAttempts(u, C),                if now - window_start <= 7 days and attempts < 5 
  RejectSubmission('Attempt Limit Met'),  if now - window_start <= 7 days and attempts >= 
5

Conclusion and Future Scope
 
6.1 Conclusion
 
In this major project, we engineered, implemented, and empirically validated SecureCode  
AI—an innovative, browser-based secure coding practice and automated assessment platform 
designed to cultivate defensive software engineering competencies from the ground up. By 
bridging the critical pedagogical gap between algorithmic competitive program ming (which 
evaluates only functional correctness) and offensive cybersecurity training (which focuses 
solely on vulnerability exploitation), SecureCode AI establishes a transformative paradigm in 
software engineering education. 
The primary conclusions and technical contributions of this project are summarized below: 
• 
 1. Efficacy of Dual-Stage Evaluation: The staged pipeline—evaluating dynamic functional 
unit tests inside an isolated Judge0 sandbox before invoking static security analyzers—
optimizes server throughput, prevents computational waste on broken code, and guarantees 
that only functionally viable solutions undergo security analysis.
 
• 
 2. Multi-Engine Security Consensus: By orchestrating Semgrep (AST syntax matching), 
SpotBugs with FindSecBugs (bytecode dataflow tracking), and Groq LLaMA-3 (contextual 
semantic advisory) within a fail-closed consensus framework, SecureCode AI eliminates the 
20%+ false-negative rate inherent in single-scanner tools, achieving zero false passes on 
vulnerable code.
 
• 
 3. Comprehensive Injection Curriculum: The development of 45 staged injection challenges 
spanning SQL, NoSQL, OS Command, LDAP, XPath, Header/CRLF, and Code Injection 
addresses the critical industry reality that while basic SQL injection is widely understood, 
diverse injection subtypes remain persistent threats in enterprise systems.
 
• 
 4. Multi-Pillar Pedagogical Scoring: The four-pillar formula (Functional 25%, Security 45%, 
Understanding 15%, Independence 15%) successfully assesses multi-dimensional 
competence. Combined with 5-attempt rate-limiting windows and tiered hint penalties, the 
platform deters brute-force guessing and rewards deliberate defensive reasoning.
 
• 
 5. Empirical Robustness and Performance: The platform was validated across 80 automated 
unit, integration, and security test suites, demonstrating sub-second median latency for local 
analysis, robust database ACID compliance across 21 Flyway migrations, and seamless 
responsive client rendering.

6.2 Future Scope
 
While SecureCode AI provides a robust foundation for secure coding education, several 
promising avenues for future expansion and research will be pursued in Semester VIII and 
beyond: 
• 
 1. Multi-Language and Memory Safety Expansion: Extend the challenge curriculum beyond 
Java to encompass memory safety vulnerabilities in C, C++, and Rust (addressing CWE-119 
Buffer Overflows, CWE-416 Use-After-Free, and Integer Overflows), utilizing LLVM 
sanitizers (AddressSanitizer, MemorySanitizer) within the dynamic sandbox.
 
• 
 2. Full OWASP Top 10 Curriculum Coverage: Broaden the active vulnerability catalog to 
cover the entire OWASP Top 10 and CWE Top 25, including Cross-Site Scripting (XSS / 
CWE-79), Insecure Deserialization (CWE-502), Broken Object Level Authorization 
(BOLA/IDOR / CWE-639), and Server-Side Request Forgery (SSRF / CWE-918).
 
•

dynamically analyzing submitted student code and synthesizing novel, adversarial edge-case 
inputs specifically tailored to expose boundary condition flaws and subtle logical bypasses.
 
•

Battles' and collaborative team-based CTF competitions where learners race to patch 
vulnerable microservices under active automated attack simulations, fostering collaborative 
problem-solving.

studies across undergraduate engineering cohorts to quantitatively measure knowledge 
retention, pre- and post-test competency gains, and real-world defect reduction during

Conceptual Understanding Automated Evaluation Rubric
 
The automated AI rubric (VulnerabilityUnderstandingService) evaluates student written 
justifications on a scale of 0 to 15 points across three dimensions:  
1. Taint Path Comprehension (0 –5 pts): Does the student accurately identify the untrusted 
source, propagation path, and sensitive sink?  

=== PAGE 63 ===
62 | P a g e 
2. Architectural Remedy Rationale (0–5 pts): Does the student clearly explain why their chosen 
defensive API (e.g., parameter binding, allowlisting) neutralizes the exploit vector?  
3. Residual Risk Awareness (0–5 pts): Does the student demonstrate understanding of defense-
in-depth principles and remaining attack surfaces?
